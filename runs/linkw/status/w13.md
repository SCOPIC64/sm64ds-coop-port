**Nothing was de-seated, because nothing needed de-seating.** All 43 bodies

## Method

`port/tools/w13_rom.py` reads the overlay image the port actually ships from
(`extracted/overlays/overlay_NNNN.bin`) at the `base_address` that
`extracted/dsd/arm9_overlays/overlays.yaml` gives for that overlay id, and takes
the body length from `config/arm9/overlays/ovNNN/symbols.txt`. Deliberately not
a dsd export reader: a dsd `arm9_overlays/ovNNN.bin` export carries relocated
words, so a literal that reads as a live pointer there is a rebasing artifact
rather than what the ROM holds.

`port/tools/w13_syms.py` resolves branch targets and pc-relative literals
against main + itcm + dtcm + the overlay's own table, overlay-first, which is
how the loaded image resolves. `port/tools/w13_dump.py` pairs each `src/` body
with its annotated ROM disassembly. Every ruling below rests on that pairing;
all 43 bodies were readable, none needed a fallback length.

Blast radius (which class, which slot, which mounted level) was censused
separately out of the `port/hal/actor_classes_ov*.cpp` fills,
`port/hal/actor_classes.inc`, `port/hal/actor_registry.cpp` and
`port_level_table[]` in `port/hal/level_boot.cpp`.

## The set that was actually at risk

Seven bodies sit in a slot that runs **every frame on a level the port mounts**:
`func_ov045_0211129c`, `func_ov045_02111274`, `func_ov052_021112ac`,
`func_ov052_02111284`, `func_ov063_0211c7b0`, `func_ov100_021470f4`,
`func_ov100_021470a4` (levels 37, 44, 12, 13, 15).

Those are the seven where a guess would have been shipping unverified behaviour
into a live frame loop. **All seven read faithful against the ROM**, each
verified instruction by instruction, so the risk did not land. That is the
answer to the question the lane was opened to ask, and it is a measurement, not
a reassurance: the disassembly for all seven is in the evidence column above and
reproducible with `python port/tools/w13_dump.py <symbol>`.

`func_ov063_0211c7b0` is worth naming separately because it is **not** in a
vtable slot at all. It is seated into furniture PMF table
`data_ov063_0211ef38[3]` and `MansionSteps::Behavior` (vt[6]) calls through that
table unconditionally every frame for the MERRY_GO_ROUND mode actor on level 12.
Same blast radius as an Update slot; the guard's slot-based reading would not
have flagged it as one.

The four ov060 bodies are dead in this build: `port_host_abi_blocked()` in
`port/hal/actor_registry.cpp` declines every BowserSkyPlatform (id 167) spawn,
and level 40 is the only level in the game that places id 167.

### Correction 1 -- the marker is wrong on all 43

Every file below carries

    recovered from vtable slot identity

on the quoted line while its body is a verified decompilation of the ROM. The
marker claims the body was inferred from what a vtable slot appeared to want. It
was not. The line should be replaced with a provenance line that says what is
actually true -- the *name* was recovered from vtable slot identity, the *body*
is decompiled -- e.g.

    /* <Class>::<Method> - name recovered from vtable slot identity;
       body verified against ROM ovNNN @ 0xADDR (run linkw w13) */

Removing the phrase is what clears these from
`port/tools/inferred_stub_debt.txt`, and the queue must reach zero.

## Cross-overlay symbol spellings -- checked, already handled

Three bodies reference a symbol under another overlay's spelling because two
overlays share a base address and another module's dsd export won the naming
race. All three are already correctly bound in the port; none is a defect:

- `src/func_ov045_021113ec.c` spells ov045's own `func_ov045_021114c8` as
  `data_ov059_021114c8`. Bound by
  `#pragma comment(linker, "/alternatename:...")` at
  `port/hal/actor_classes_ov045.cpp:391`.
- `src/func_ov052_0211123c.c` spells ov052's own file table
  `data_ov052_021124d4` as `data_ov056_021124d4`. Remapped by
  `COMPILE_DEFINITIONS` at `port/CMakeLists.txt:777`.
- `src/func_ov100_02146dec.cpp` and `src/func_ov100_021471e0.cpp` reference
  `data_ov002_0210af70` / `0210d9f0` / `0210d7d4`. ov002 is resident alongside
  the level overlays, so these are genuinely ov002 addresses and correct as
  spelled.

The `VT0`/`VT1`/`VT2` and `G0`/`G1`/`G2` shared placeholders in the D0 bodies
are per-TU names, not one object. `port/hal/actor_vtables.cpp:336-344` keeps
`VT0`/`VT2` as zeroed storage on the documented ground that these stores are
"installed transiently during teardown and never dispatched", and warns in the
same comment that a slot which IS dispatched must never come through one. Every
such store in these 43 sits between two direct calls in a teardown chain with no
dispatch in between, so the reading holds here. `G0` is the game heap, aliased
to `data_020a0eac`, which is the word the ROM literal pool actually holds at
each of those slots (verified in the disassembly above).
