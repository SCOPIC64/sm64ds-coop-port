THE STAGE LIFECYCLE: what hal/level_boot.cpp does that the ROM's Stage does,
which half is scaffolding and which half is genuinely the host's, and what
each lifecycle phase is actually blocked on. Run link60, lane L4.

Baseline this was measured against: 0d81b845c, walk_window 4950 / 11243 linked
(44.0%), battery ALL GREEN, gate GREEN, skips [scene 4 SM64DS_SCENE_SLOT9=0].
arm9 3098 matched TUs, 1664 linked, 1434 unlinked. No exe sha256 is quoted:
the link embeds build-location state, so a hash from one worktree is not a
number another worktree reproduces (the attestation is the gate manifest's
git_sha plus git_dirty).

Every "unresolved" list below was PRODUCED BY A LINK, not read off an earlier
note. The method is the same each time: wire the TU into walk_window in a
throwaway CMakeLists edit, build, read link.exe's own error text, revert. Three
of the counts in port/arm9_frontier.txt and port/slice_w8a.txt have moved since
they were written and one of them was wrong in a way that matters; both are
corrected below with the measurement attached.


0. THE ONE-LINE ANSWER
----------------------

The Stage's whole lifecycle is behind ONE gate, and it is not the vtable.

  * The vtable is not the problem. hal/stage_bridges.cpp already hosts
    _ZTV5Stage and trap-fills it, and thirteen of its eighteen slots have a
    body that closes against today's link with nothing added.
  * The dispatch is not the problem either. The port already runs all five of
    the ROM's processing passes over the ROM's own list structures
    (hal/actor_registry.cpp, the four Process host copies in port/unmatched/).
  * An actor reaches the behaviour and render lists ONLY by surviving the init
    Process. func_02043880 (phase 1, matched, linked) moves a node onto
    data_020a4b78 and data_020a4b98 when the actor's +0x10 is set, and +0x10 is
    set by the init pass succeeding. So slots 6/7/8 and 9/10/11 are downstream
    of slots 0/1/2.
  * Slot 0 is Stage::InitResources, and it does not close: THIRTY unresolved
    externals, enumerated in section 4.

So "seat the Stage vtable" and "route the boot through the ROM's lifecycle"
are not two jobs that can be done in either order. The init phase is the whole
lane, and everything after it is downstream of one function.

2. THE SEAM, FUNCTION BY FUNCTION
----------------------------------

port_stage_a_boot (hal/level_boot.cpp:2154-2332) against
Stage::InitResources (src/_ZN5Stage13InitResourcesEv.cpp, 0x0202cc0c, marked
NONMATCHING TERMINAL-FLOOR: four words diverge, a register-rename-only delta).

Reading the two side by side, the boot is a SUBSET with three substitutions.
It is not a reimplementation: every line of it either calls the same matched
body the ROM calls, or stands in for one, or supplies an input the ROM gets
from a mode the port never entered.

3. A CORRECTION THIS MAP OWES TWO OTHER FILES
----------------------------------------------

port/arm9_frontier.txt line 337 says the four Stage vtable slots "are already
COMPILED (they sit in DROPPED, offered and dropped for want of a reference)".
FOR Stage::InitResources THAT IS NOT TRUE, and the difference matters because
the frontier reads it as the cheap half of the move.

src/_ZN5Stage13InitResourcesEv.cpp is named by port/slice_gate36.txt, which is
what puts it in the survey's DROPPED bucket -- the bucket test is "named in a
slice_*.txt". But SLICE36_SOURCES is parsed into a variable and added to NO
target (port/CMakeLists.txt:3160, and the block above it says so at length).
Checked directly: `_ZN5Stage13InitResourcesEv.cpp.obj` does not appear in
build/port/build.ninja. It is not compiled, it is not offered to the linker,
and it is not dropped by /OPT:REF. The same is true of fifteen more gate-36
lines that the survey counts as DROPPED: ResetInput, UnloadArchive,
LoadDebugFont, LoadLevelOverlays, ResetKuppaScript, IsLevelInsideCastle,
IsLevelTinyHugeIslandOutside, Stage::SetVramBanks, Stage::LoadFog,
func_02039218, func_020308a8, func_0203da3c, func_0203dad4, the three
FaderWipe TUs.

BeforeInitResources, D0 and D2 -- the other three the frontier names -- ARE
compiled, from slice_w8a.txt, and for those the frontier is exactly right.

This is a survey measurement bug (DROPPED is derived from slice TEXT, not from
the build) and not a claim about the port. port/tools/objsrc_check.py reads
build.ninja and is the tool that would settle it; nobody has pointed it at the
DROPPED bucket. Left as a finding rather than fixed, because the fix moves
every lane's bucket counts mid-stage.

port/slice_w8a.txt's blocked list is also stale in the direction of pessimism.
It rules Stage::CleanupResources blocked on "the storage the fader closure
needs -- _ZTV9FaderWipe, the table hal/fader_wipes.cpp stages by hand, and
_ZN5ColorD1Ev". Measured today, CleanupResources wants SIX symbols and neither
_ZTV9FaderWipe nor _ZN5ColorD1Ev is among them (section 5). The fader
dependency is real but it arrives through _ZN9FaderWipeD1Ev, one level down.

    func_02018908            under UnloadArchive

    func_02023408            under LoadDebugFont

DECLINE, RECORDED HERE SO IT IS NOT RE-DERIVED. Two of the thirty cannot be
closed by enrolling anything, because the thing they name does not exist on
the host:

  * LoadLevelOverlays(int) walks a table of DS overlay ids and calls
    LoadOverlay on each. The port has no overlay loader -- every overlay it
    hosts is a static host array mounted at build time (port/scene_boot_map.txt
    section 2 states the same rule for the scene overlay load: "THE OVERLAY
    LOAD IS NOT SKIPPED, IT DOES NOT EXIST ON THE HOST"). Its host occupant is
    port_level_mount. Seating the matched TU means hosting a loader to produce
    a load the mount already performed.
  * UnloadArchive / LoadArchive reach data_0208ecf4, whose 26 relocations are
    DS string pointers into the card filesystem, and LoadArchive is already a
    tagged PORT_HOST_ABI host body in hal/scene_boot.cpp for the reason that
    file states: the port resolves archive-interior file ids lazily and an
    archive is "never mounted and never not mounted". Linking src/LoadArchive.c
    raises LNK2005 against that host body -- measured.

WHAT THAT MEANS FOR SLOT 0. Stage::InitResources calls both of them directly.
So slot 0 cannot be seated as the matched body without either (a) two host
faces standing in for LoadLevelOverlays and LoadArchive at the C-name level,
which is trading one piece of scaffolding for two smaller ones inside the ROM's
own call, or (b) an overlay loader and an archive mounter the port has decided
twice, in two other lanes' files, not to have.

That is this map's ruling: SLOT 0 STAYS HOSTED AT THIS BASELINE, and the reason
is an architecture decision two other files already made and this lane is not
overturning from the outside. What CAN move is everything the gate was hiding,
which is section 7.

deferral with a hope. Note the shape: the port's Stage does no behaviour at all

behaviour-neutral, and the port's Stage rendering is walk_window's own

would move where the call is made without changing what is drawn. Both are
available and both are NEW scaffolding, which is why neither is in section 7.


7. WHAT ACTUALLY MOVES, AND IN WHAT ORDER

already-closing slots REAL rather than the ones that force slot 0:

  T1  THE MAP. This file.

  T2  SEAT THE THIRTEEN SLOTS THAT CLOSE, into the table
      hal/stage_bridges.cpp already hosts, and make the init dispatch real by
      routing the boot through func_020433b8 -- the ROM's own "thread it onto
      the init list" entry point, which is what the spawn spine calls for
      every other actor. That runs slot 1 (Stage::BeforeInitResources, matched)
      and slot 2 (Scene::AfterInitResources through the existing face) on every
      level boot, dispatched by the ROM's init Process. Slot 0's occupant is
      the boot body the port already has.
      This is not a fake edge: the init Process is matched code, it is already
      driven every frame, and the two slots really execute. What it does NOT
      do is retire scaffolding, and section 8 says so.

  T3  THE LISTS. Surviving the init pass sets +0x10; phase 1 (func_02043880,
      matched, linked) then threads the Stage onto data_020a4b78 and
      data_020a4b98. Slots 7/8/10/11 are Scene halves that are ALREADY LINKED,
      so this costs nothing new and RETIRES the one real piece of scaffolding
      in reach: hal/stage_bridges.cpp's `*(g_stage + 0x13) &= ~(1|4)`, which
      that file already documents as a stand-in for exactly one statement
      inside Scene::BeforeBehavior. Slots 6 and 9 need an occupant (section 6).

  T4  THE FACES AND THE PURE-DATA ROWS from section 4 that are useful on their
      own -- the three C-name faces onto already-linked bodies, and the
      zero-relocation romdata rows. They do not seat slot 0 and they are not
      offered as progress toward it; they are offered as the part of the
      closure that is measurable and safe.

  NOT IN SCOPE HERE, and named so the next lane does not rediscover them:

8. WHAT THIS MAP DOES NOT CLAIM
--------------------------------

  - That T2 retires anything. It does not. It makes two matched bodies run
    that did not run, and it puts the Stage where the ROM puts it. The
    scaffolding in port_stage_a_boot is still there afterwards, because slot 0
    is still the boot body.
  - That the port's 2D register state after a real Stage::InitResources would
    match today's. Section 2c lists eight raw I/O writes and nobody has
    measured what the ntr layer does with them.
  - That the ~490 arm9 TUs port/arm9_frontier.txt hangs off the four Stage
    roots arrive with T2 or T3. They hang off slots 0, 3, 6 and 9, and all
    four of those are declined above. The transitive estimate is also stale:
    it was computed against a tree with 1634 arm9 TUs linked and this one has
    1664.
  - Anything about the levels. Every number here is a link measurement. The
    battery is the only thing that speaks for behaviour, and it speaks per
    commit, not here.
