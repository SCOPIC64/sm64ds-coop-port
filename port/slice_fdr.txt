# Lane FDR: THE arm9 WIPE FADER'S OWN STATIC INITIALISER. Run link60 Stage 4.
#
# The blocker this retires is port/tools/battery.py's SCENE_BLOCKED row for
# scene 374: dScMgBase_c's slot 1 hands data_0209f61c to Scene::SetFaders, and
# that object's vptr was zero because the port never ran the ROM's initialiser
# for it. The fix is to RUN it, not to reimplement it, so what is listed here
# is the initialiser and the bodies its vtable names -- nothing else.
#
# THE OBJECT IS A dWipe_c, not a FaderBrightness. The handover, MG2's write-up
# and the SCENE_BLOCKED row all say FaderBrightness; the ROM's own RTTI at
# 0x020926dc says "7dWipe_c", deriving dFdColor_c -> dFdBrightness_c ->
# dFader_c. FaderBrightness IS dFdBrightness_c, two levels up, so it is the
# grandbase and dFader_c is the third level. The addresses in every one of
# those documents are right; only the class name is wrong. The full derivation
# is in the header of port/hal/fdr_arm9_fader_seat.cpp and the closure is in
# port/fader_boot_map.txt.
#
# THE FADE MOTION ARRIVED IN THE SECOND CHUNK, run link60 lane FDR2, and it is
# the block of nine at the foot of this file. Slots 0x0c and 0x10 are the ROM's
# own bodies now. What that pulled in was measured with port/tools/closure.py
# rather than estimated: NINE TUs and NINE unhosted data symbols, where the
# note this replaces said "four arm9 data symbols". Two of the nine are arm9
# .data and come from port/tools/romdata.py (data_020926c8, data_020926cc); the
# other seven are bss and are hosted in the seat's own .dsstate block.
#
# WHAT IS NOT HERE AND WHY:
#
#   src/func_0202f428.c   slot 0x08  AdvanceFade
#     STILL A TRAP, and this is a ruling rather than a scheduling call. The
#     body is a faithful decomp (ruled against the ROM in
#     port/tools/inferred_stub_adjudicated.txt) but it carries the same
#     host-broken edge as src/func_0202ed08.c below: its `type == 1` branch
#     calls `_ZN10FaderColor11AdvanceFadeEv()` with NO ARGUMENT, because the
#     ROM's `bl` leaves r0 alone and the receiver rides through. Seating it
#     would put a receiver-dropping call into the build. It buys nothing that
#     would pay for that: slot 0x08 has no call site anywhere in the image
#     (port/fader_boot_map.txt section 9a enumerates them), and the closure it
#     would add beyond the nine below is itself plus FaderColor::AdvanceFade.
#     port/tools/closestplayer_guard.py now carries a rule for the symbol, so
#     the day somebody puts this TU in a slice the build refuses instead of
#     shipping the call.
#
#   src/func_0202ed08.c   slot 0x20  SetToEnd
#     HOST-BROKEN, and this is a decomp-side finding rather than a scheduling
#     one. The ROM body is a bare tail-call veneer (ldr ip,[pc]; bx ip; .word
#     0x0201761c) and the src spells it `func_0202ed08(void)` calling
#     `_ZN15FaderBrightness8SetToEndEv()` with no argument at all. Under mwccarm
#     that is byte-correct because r0 falls through a bx; on the host the
#     receiver is simply gone. Identical in shape to the Heap::_Destroy veneer
#     lane LK4 wrote up in hal/lk4_solidheap_seat.cpp. The slot forwards to the
#     veneer's own target instead, with the receiver.
