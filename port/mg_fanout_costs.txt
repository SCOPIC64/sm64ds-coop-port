1. THE HEADLINE, AND THE CORRECTION IT RESTS ON
------------------------------------------------

ov006 is the largest single prize left (1839 matched TUs) and
port/ov006_minigame_scout.txt section 5 ranked the thirty minigame ids by
closure size so the fan-out could start with the smallest. THAT RANKING IS
BUILT ON A CLOSURE THAT MISSES EVERY MINIGAME'S STATE MACHINE, and the
correction is the most useful thing in this file.

The scout rooted each id at its SpawnInfo record. A minigame's states are mwcc
POINTER-TO-MEMBER PAIRS: eight-byte {code, adjustment} records that live in
.data and are copied at overlay-load time, by the overlay's own .init
constructor, into .bss dispatch tables. Neither end of that is reachable from
the SpawnInfo. The .bss destination carries no relocations at all -- it is
zero-initialised storage -- and the .data source is reached only from .init.
So a walk from the SpawnInfo reaches the class's vtable and the vtable's
bodies, and then stops dead before the thing the class spends its frames in.

Measured on the pathfinder's own class, both ways:

    roots                          ov006 fn   ov004 fn   arm9 fn
    SpawnInfo only (the scout's)         17         97       547
    SpawnInfo + its own .init            48        160       560

The scout costed this minigame at "19 TUs". Its real closure is 48 + 160 = 208
ov006 and ov004 functions, of which 202 have a matched src TU. The scout's
ov006 column is low by 2.8x and its ov004 column by 1.6x.

THE RANKING SURVIVES ANYWAY, AND THAT IS WORTH SAYING PLAINLY. Section 3's
per-class table re-ranks on the vtable axis and MgShuffleShell is still among
the cheapest four, so the peer screening picked a correct target from an
incorrect number. The number still has to be fixed, because the fan-out is
about to cut twenty-nine more lanes from it.

4. THE WALL, AND IT IS THE SAME ONE FOR ALL THIRTY
---------------------------------------------------

A minigame's Behavior does this, and every one of the thirty does some version
of it (src/func_ov006_020e3528.cpp, dScMgCurling_c slot 6, verbatim):

    int j = c->idx;
    (c->*data_ov006_02141950[j].pmf[0])();

That is an mwcc POINTER-TO-MEMBER call and the port cannot compile it. Three
separate reasons, and each alone is fatal:

  1. THE STRIDE IS WRONG. mwcc's member pointer is eight bytes, {code,
     adjustment}. MSVC's single-inheritance member pointer is four. The src
     spells the table `struct Entry { PMF pmf[1]; }`, so MSVC strides the array
     by 4 where the ROM strides by 8, and every index past 0 reads half of one
     record and half of the next.
  2. THE WORD IS A DS ADDRESS. The table is filled by the overlay constructor
     from .data statics holding raw ROM code addresses. Verified word for word
     for this class: all twenty-five of __sinit_ov006_021304ac's source pairs
     at 0x0213c1e4..0x0213c2bc read {code, 0} in the image.
  3. THE DISPATCH IS THE FULL ARM ITANIUM SEQUENCE, virtual bit in the
     adjustment's LSB and `this` advanced by the adjustment arithmetic-shifted
     right one. The ROM emits five instructions for it. MSVC emits its own,
     incompatible, shape.

THE WALL IS NOT ONLY ov006's, AND THAT IS THE FINDING THAT CHANGES THE
SEQUENCING. It was assumed above that the pointer-to-member problem was each
minigame's own state machine. It is not: the FRAMEWORK has one too, and the
framework's is the one a boot hits first.

src/func_ov004_020b87e0.cpp is dScMgBase_c's STATE SETTER -- sixty-three lines
that build a static table of twenty member pointers out of twenty ov004
globals, assign one into the object and dispatch it. It produced TWENTY-ONE of
the first link's ninety-five unresolved externals, all from that single TU, and
the mangling says exactly why:

    unresolved external symbol "void (__thiscall C::* data_ov004_020bc97c)(void)"
      (?data_ov004_020bc97c@@3P8C@@AEXXZQ1@)

MSVC encodes the member-pointer TYPE into the symbol name, so a global the ov004
mount emits as the C symbol _data_ov004_020bc97c can never satisfy it. And that
is the mildest of the three problems: the TU's own `struct C` puts field_8 at
+8 after a leading member pointer, which is only true at eight bytes, so MSVC
lays the object out wrong before any dispatch happens.

SO EVERY MINIGAME NEEDS THIS ONE TU SOLVED, and it is paid once. It is excluded
from port/slice_mg1.txt and stands as a named trap in hal/scene_mg_faces.cpp
that reports itself and sets no state. Solving it is worth more than any single
minigame: it is one 63-line host copy plus twenty routed addresses, and it
unblocks the framework half of all thirty.

THE PORT ALREADY HAS THE ANSWER AND IT IS NOT CHEAP. port/unmatched/
Player_ChangeState.cpp is the precedent: a host copy of the dispatching TU with
the member-pointer site replaced by an address switch, plus
hal/player_bridges.cpp's hal_call_state_fn, a 197-case generated switch from
DS address to a real __thiscall method call. The alternative precedent is the
ov085 / ov100 shape, port_*_states_seat, which writes HOST addresses over the
.data source pairs before the constructor copies them -- but that one still
needs a host copy of the dispatcher, because the stride is wrong either way.

5. WHY THE arm9 COLUMN IS NOT A COST
-------------------------------------

The pathfinder's closure reaches 560 arm9 functions and 558 of them already
have matched TUs compiled into the build. They come back through /OPT:REF for
free the moment ov004 or ov006 references them, exactly the way the ov007
lane's 92 did, so listing them as slice lines would be 558 lines that change
nothing. They are not in port/slice_mg1.txt and the file says so.

THE COROLLARY IS THE TRAP THE SCOUT ALREADY NAMED AND IT APPLIES TO THE .init
CONSTRUCTORS TOO. Wiring a TU that nothing references buys nothing: /OPT:REF
strips it. The constructors in this lane are referenced -- hal/scene_mg.cpp
calls all thirty-three by name -- but the state functions their pair tables
point at are NOT, because the pair words are mounted DATA holding DS addresses
and no host symbol names them. So the ov006 linkage this lane buys comes from
the vtable seat and the constructors, and the several hundred state bodies stay
gated behind section 4's dispatch. That is the honest reading of any ov006
delta this lane reports, and it is why the dispatch is the next lane and not an
optimisation.


6. THREE DEFECTS FOUND ON THE WAY, ALL LIVE, NONE VISIBLE TO THE BYTE GATE
---------------------------------------------------------------------------

Found by the twenty-five ROM adjudications rather than by running anything, and
recorded here because each bites a specific fan-out lane at a specific moment.

  a. A DECLARATION CONFLICT THAT STOPS THE BUILD. include/decl_common.h lines
     2342 and 2343 declare func_ov004_020aeed8 and func_ov004_020af094 with
     void*, and both src TUs define them with char* and Obj* respectively while
     including that header. MSVC refuses each with C2733; mwccarm accepts it,
     which is why the ROM built and the byte gate has never had an opinion.
     FIXED HERE, by two host copies in port/unmatched/MgBase_DeclConflict.cpp
     that are the src bodies verbatim with ONE TOKEN CHANGED EACH, stated line
     by line in that file's header. The header fix proper is a five-file change
     inside the byte-gated tree -- two callers carry their own conflicting
     local declarations -- and is routed, not taken.

  b. A DROPPED `this` ON SLOT 7. include/decl_Scene.h declares
     `extern int _ZN5Scene14BeforeBehaviorEv();` with EMPTY PARENS inside
     extern "C", so src/func_ov004_020b0620.cpp's call at line 52 passes no
     object pointer, while the real definition
     (src/_ZN5Scene14BeforeBehaviorEv.cpp:47) takes `char* self` and
     dereferences it immediately. On ARM this is a ride-through and correct --
     r0 already holds self. On the host the callee reads the stack. The line
     ABOVE it in the same header spells the sibling correctly,
     `_ZN5Scene19BeforeInitResourcesEv(void*)`, which is what makes this a
     defect rather than a convention. NOT FIXED HERE, and it is a blocker for
     the first lane that dispatches slot 7 of any minigame table -- which is
     every one of them, since dScMgBase_c owns that slot.

  c. A DELETE WITH NO POINTER ON SLOT 5. src/func_ov004_020b0840.c:12 declares
     `extern void func_0203cbc0(void);` and calls it with no argument at line
     28, while the ROM has the pointer being deleted live in r0. The port's own
     host body is `func_0203cbc0(void *p) { _ZdlPv(p); }` in
     port/unmatched/func_02073244_hostcopy.c, so the call hands operator delete
     whatever is on the stack. Seven other src TUs declare the same function
     WITH a pointer parameter. Same ride-through family as (b). NOT FIXED HERE.

  Both (b) and (c) want the same remedy as (a): a PORT_HOST_ABI host copy in
  port/unmatched/ that places the argument, leaving src/ and the byte gate
  alone. Neither was taken because neither can be EXERCISED until section 4's
  dispatch exists, and a host copy nobody can call is a count rather than a
  port. They are named here so the next lane meets them as known work.

  A FOURTH, SMALLER: src/func_ov006_020e3578.c spells ov004's
  func_ov004_020adc74 as bare `func_020adc74`, a name that exists in no config.
  The reloc says module overlays(3,4) and ov004 is the co-resident answer. A
  name-spelling face, the ordinary kind.
