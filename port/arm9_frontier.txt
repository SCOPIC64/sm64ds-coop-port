ARM9 LINKAGE FRONTIER -- what stands between the port and the other 1450
========================================================================

Run linkw wave C, lane cat-arm9. Measured on the tree this file ships in,
at the lane baseline commit 459f21a07, against the gate manifest at
build/port/gate_manifest.json:

    linkage headline   4888 / 11243 linked (43.5%)
    arm9               3098 matched TUs, 1648 linked, 1450 unlinked (53.2%)
    battery            ALL GREEN
    gate verdict       GREEN

Reproduce any number below with

    python port/tools/cat_arm9_survey.py [--roots] [--list BUCKET]
    python port/tools/objsrc_check.py

Both root at the checkout they live in, not at the current directory.


THE SHORT VERSION
-----------------

arm9's 1450 unlinked TUs are not 1450 problems. 58% of them sit downstream of
SIX functions, and every one of those six is a piece of the ROM's own boot and
frame spine that the port replaces with host code on purpose. The workable set
-- TUs a lane could seat this week without changing what the port boots -- is
FIFTY-SIX, and reading them one by one, almost all are blocked on something
other than effort.

There is no batch of easy arm9 links available at this baseline. Saying so with
the evidence attached is this lane's result. Manufacturing the links would have
meant writing callers the ROM does not have, which is the exact failure this
campaign exists to prevent.


THE BUCKETS
-----------

Every unlinked arm9 TU falls in exactly one, tested in this order. The columns
reconcile with the headline above on purpose.

    SHADOW          0    a host file defines the symbol, the matched TU is not
                         in the binary, and no PORT_HOST_ABI tag rules it an
                         exception. This is the replacement work list, and for
                         arm9 it is now empty -- see THE THREE SHADOWS below.
    DROPPED        52    offered to the linker (named in a slice_*.txt or a
                         CMakeLists symbol set) and dropped by /OPT:REF for
                         want of a reference edge.
    CANDIDATE       4    never offered, but a LINKED TU references its ROM
                         function. The edge exists; the object does not.
    TABLE-ONLY    124    never offered, no call reloc reaches it, and a data
                         word does. A vtable or dispatch-table slot.
    UNREACHED     999    never offered, has ROM callers, none of them linked.
    OV-ONLY       136    never offered, and every ROM caller lives in a module
                         the port does not mount.
    ORPHAN         26    never offered, no call reloc and no arm9 table word
                         reaches it.
    EXCEPTION     109    a documented host-ABI exception: an ARM asm primitive,
                         a register ride-through, an mwcc pointer-to-member
                         dispatch, or a poke of DS hardware the ntr layer does
                         not model. Not work.

    TOTAL        1450


HOW REACHABILITY IS DERIVED, AND ITS ONE LIMIT
----------------------------------------------

Callers come from config/*/relocs.txt. delinks.txt cuts arm9 one function per
file, so every call between two functions crosses a file boundary and the
delinker recorded it. That is the ROM's real call graph.

It holds only CODE relocations, though: all 13891 arm9 rows are an arm_call or
a PC-relative load, and not one is a data word, because arm9 is not relocated
at runtime and a vtable's slots are plain absolute addresses in .data. Read
alone it answers "nothing references it" for every method reached only through
a vtable. So the survey also scans arm9's own .data/.rodata for words landing
on a function's first byte -- 425 arm9 functions are reached that way and no
other. .exception and .exceptix are excluded: a function is listed there
because it has a cleanup range, not because anything reaches it, and left in
they hand 53 functions a caller that does not exist.

THE LIMIT. "A linked TU references it in the ROM" is proof the ROM makes the
call. It is NOT proof the port's copy of that caller still makes it -- the host
build may reach the same point through a host body. Every CANDIDATE row is a
hypothesis until it is compiled and the map is read.


THE FRONTIER: 394 ROOTS, AND SIX THAT MATTER
--------------------------------------------

A root is an unlinked arm9 TU with no unlinked caller of its own. Pushing
anywhere else is wasted -- the linker drops a TU whose caller it also dropped.
There are 394. Sorted by how many unlinked arm9 TUs become transitively
reachable if the root links:

     531  func_0203506c                    0x0203506c
     528  func_02005a58                    0x02005a58
     483  func_02030b58                    0x02030b58
     479  func_02030c38                    0x02030c38
     182  _ZN5Stage8BehaviorEv                         Stage vtable slot
     162  func_02034da4                    0x02034da4
     146  _ZN5Stage13InitResourcesEv                   Stage vtable slot
      89  func_02005418                    0x02005418

      54  LoadFont3D
      50  func_0201817c
      47  _ZN13SharedFilePtr4LoadEv

The union of the top six covers 835 of the 1450 -- 58%.

Read the list and the answer to "why is arm9 only 53% linked" stops being a
matching question. The port does not run the ROM's boot, and it does not run
the ROM's Stage lifecycle: walk_window.cpp drives a host frame loop that calls
into the pieces, and hal/w8a_stage_faces.cpp plus hal/level_boot.cpp stand in
for the Stage the ROM would have built. Everything hanging off Entry and off
the four Stage slots is unreachable until the port adopts the real spine. That
is a campaign, with a behaviour story per step, not a lane's worth of seating.

The four Stage slots are the nearest edge of it: they are already COMPILED
(they sit in DROPPED, offered and dropped) and their ROM home is _ZTV5Stage,
which the port hosts. Seating them is a linkage change of ~490 TUs and a
behaviour change to everything the port boots, in that order of importance.


THE WORKABLE SET, READ ONE BY ONE
---------------------------------

SHADOW (0). There were three, and all three turned out to be untagged
documented exceptions rather than work:

    func_0203cbc0   port/unmatched/func_02073244.c    ARM ride-through: src
                    spells it `void func_0203cbc0(void)` calling `_ZdlPv()`
                    with no argument, correct on ARM where the pointer is
                    already in r0.
    func_020432e4   port/unmatched/func_0204322c.cpp  mwcc pointer-to-member:
                    ActorBase::Process called with three PMFs.
    func_020441cc   port/unmatched/func_02043fdc.cpp  mwcc pointer-to-member:
                    the list head carries its callback as a PMF pair.

Each host file already explained itself in its header comment; none carried a
PORT_HOST_ABI tag on the definition, which is the only place linkage.py's tag
reader looks. This lane added the four tags (the three above plus func_02042ffc
in port/unmatched/ActorDerived_Spawn.cpp). Comments only, no behaviour change,
no link change. The tag is a ruling about the SOURCE, so the survey reads tags
from host sources directly rather than from the map -- func_02042ffc is the
case that forced that: MSVC folds its body into the one-line wrapper above it,
so no symbol of that name reaches the map at all.

CANDIDATE (4). All four have a linked ROM caller and none is work:

    _ZN15ModelComponents6RenderEP9Matrix4x3P7Vector3
        port/unmatched/ModelComponents_Render.cpp is a documented host
        reimplementation. src calls the material bind as `func_02044b30(this)`
        and lets the material index ride to the callee in r1.
    func_02073300
        an asm hatch -- a reverse destructor loop with an MSL exception frame.
        There is no C to compile.
    _ZN13SharedFilePtr19ReallocateModelFileEv
        hal/gx_upload_bridge.cpp hosts it as an empty body on the true
        observation that the reallocation is a DS heap shrink. See the note in
        hal/cxxname_bridge.cpp.
    _ZN5Sound21UnsetPlayerVoiceGroupEv
        hal/auto_bss.cpp hosts an empty stub; the caller EndKuppaScript is
        linked but reaches the MSVC-namespace mangling, not the ROM C name.

DROPPED (52). Compiled and dropped for want of a reference edge. By what
would have to change for the edge to exist:

    38   every ROM caller is itself unlinked -- downstream of the spine above.
     8   a vtable slot with no call reloc: four are _ZTV5Stage (InitResources,
         BeforeInitResources, D0, D2), plus Stage::OnPendingDestroy,
         Stage::GraphCallback1, CommonModel::D0 and CapEnemy::D2.
     5   the ROM caller's port body is a host stand-in that open-codes the
         call, and in each case the stand-in exists BECAUSE of an ABI break:
         func_02017e48 (SharedFilePtr::Construct's r1 ride-through, excluded on
         purpose in slice_gate3b.txt), func_0201a03c (reached from the ROM's
         Crash and main, both replaced by the host), func_0203ad6c (the whole
         body of PathPtr::FromID's two-word struct return -- the ride-through
         itself), _ZN4cstd10fdiv_asyncE5Fix12IiE5Fix12IiE (a thin wrapper over
         the DS hardware divider) and
         _ZN9ActorBase7ProcessEMS_FivEMS_FbvEMS_FvjE (the PMF dispatch).
     1   _ZN4Heap11_DeallocateEPv has a linked caller, _ZdlPv, and is itself an
         ARM tail-call veneer -- `void _Deallocate(void)` branching to
         Deallocate with the arguments riding in registers. The MSVC-method
         face in hal/cxx_aliases.cpp is the correct stand-in. Retiring the face
         in favour of the matched body is not possible: the matched body cannot
         take its arguments.

CommonModel::D0 is the one row here that is a real seating decision rather
than an ABI wall, and it is already answered in the negative in
hal/actor_classes_bob_world.cpp: the ROM table is {D1, D0, DoSetFile} and the
host fill puts DoSetFile in slot 1 so MSVC-numbered callers (which see a folded
destructor slot) land on it. Seating the real D0 there breaks those callers.
The file says so; this lane agrees and did not touch it.


A HEADLINE OVER-CLAIM, FOUND ON THE WAY
---------------------------------------

An MSVC /MAP names an object by BASENAME only. CMake keeps src/func_02043fdc.cpp
and port/unmatched/func_02043fdc.cpp in different object directories; the map
keeps no trace of that. linkage.py counts a matched TU as linked when an object
of its stem appears in the map, so for those files it counts the HOST STAND-IN
as decompiled code reaching the game while src/ is not in the binary at all.
The same collision hides them from the replacement queue, which decides "is
this a host object" by asking whether the object's stem collides with a src/
TU -- for these files exactly backwards. That is why linkage.py --queue reports
two shadows repo-wide and this survey found three more in arm9 alone.

build.ninja records each object's real source. Measured through it:

    HOSTGEN   151 objects are hostgen's rewrite of the matched TU. Counting
              those as linked is correct -- they ARE the matched code.
    HOST       18 objects are host stand-ins counted as linked matched TUs.

So the current headline reads 4888 and the honest figure is 4870. The error is
0.16% and it is not the point; the point is that those 18 are also 18 rows the
replacement queue never prints. Six of them are arm9. Fixing linkage.py's host
detection would change every lane's numbers mid-wave, so this lane left it
alone and shipped the measurement as port/tools/objsrc_check.py instead.


WHAT WOULD ACTUALLY MOVE ARM9
-----------------------------

In the order the evidence supports, not the order of effort:

1.  The Stage lifecycle. Four slots already compiled, ~490 TUs downstream, one
    hosted vtable (_ZTV5Stage) to seat them into. This is the single largest
    honest arm9 move available and it is a behaviour campaign: every seated
    slot replaces host boot code that exists because the real one needed
    subsystems that were not there yet. Needs a lane that owns level_boot.cpp
    and the Stage faces together.

2.  The 124 TABLE-ONLY entries. Each is a vtable or dispatch slot with a
    matched body and no caller edge. They cannot be reached by adding calls --
    only by seating them in a hosted table -- and the tables are spread across
    the actor-class files that other lanes own. This is the largest set that is
    mechanical rather than behavioural, and it wants ONE lane holding all the
    vtable fills at once, not six lanes each seating into a file they share.

3.  The 136 OV-ONLY entries. Reachable only by mounting more overlays; that is
    the overlay lanes' axis, not arm9's.

4.  Fixing linkage.py's object-to-source rule, between waves rather than during
    one, so the queue and the headline stop disagreeing with the build.
