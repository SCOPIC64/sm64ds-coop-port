1. THE CLASS, AND THE ONE THING THE HANDOVER GOT WRONG

MG2's report, port/mg_fanout_costs.txt section 10 and battery.py's old
SCENE_BLOCKED row all describe data_0209f61c as "an arm9 FaderBrightness". It
is a dWipe_c. The ROM says so, in its own RTTI, with config/arm9/relocs.txt
applied to extracted/arm9_dec.bin (flat, base 0x02004000):

    0x020926dc  __si_class_type_info   name "7dWipe_c"           base 0x0208ea00
    0x0208ea00  __si_class_type_info   name "10dFdColor_c"       base 0x0208ea24
    0x0208ea24  __si_class_type_info   name "15dFdBrightness_c"  base 0x0208e9e0
    0x0208e9e0  __class_type_info      name "8dFader_c"
    0x0208ea18  __si_class_type_info   name "9dFdWipe_c"         base 0x0208ea00

    dFader_c <- dFdBrightness_c <- dFdColor_c <- dWipe_c

which is exactly the four vptr stores func_0202fc40 makes, in base-to-derived
construction order, and which also identifies the three sibling tables the port
already hosts by number rather than by name:

    data_0208eafc = _ZTV8dFader_c            hal/scene_boot.cpp:702, ROM bytes
    data_0208eacc = _ZTV15dFdBrightness_c    hal/scene_boot.cpp:693, trap-filled
    data_0208eb2c = _ZTV10dFdColor_c         hal/scene_boot.cpp:688, trap-filled
    _ZTV9FaderWipe (config name) = _ZTV9dFdWipe_c, 0x0208ea9c

NOTHING IN THE HANDOVER'S CONCLUSIONS CHANGES. Every address MG2 gave is right,
including the one that matters most ("a host fill for data_020926f0, which is
NOT _ZTV9FaderWipe"). What changes is what a successor searches for: a lane
told "FaderBrightness" goes looking in the 0x02017xxx fader engine, and none of
the ten bodies is there.

    and 00c08810 is _data_0209f61c in walk_window.map (auto_bss.cpp.obj), so

WHY 0x24, off the compiled binary rather than off the C. src/_ZN5Scene9SetFaders
EP15FaderBrightness.cpp declares a local `struct Scene` with ten virtuals and
calls thiz->v24(); MSVC puts that at byte 0x24, which under the ROM fader slot
order is SetToStart. The first 0x27 bytes of the host function, disassembled
out of walk_window.exe:

    +0x00  push ebp / mov ebp,esp
    +0x03  mov  ecx, [0xc0999c]           data_0209f5bc, the INSTALLED fader
    +0x09  test ecx,ecx / je +0x74        the ROM's own null guard
    +0x0d  mov  eax, [ecx]                its vptr
    +0x0f  push esi                       the callee-save, NOT an argument
    +0x10  push ecx                       CDECL: receiver on the stack
    +0x11  mov  eax, [eax + 0x14]         IsAtStart, by ROM byte offset
    +0x14  call eax
    +0x19  test eax,eax / je +0x36
    +0x1d  mov  esi, [ebp + 8]            thiz, the NEW fader
    +0x20  mov  ecx, esi                  THISCALL: receiver in ECX
    +0x22  mov  eax, [esi]                its vptr
    +0x24  call dword ptr [eax + 0x24]    SetToStart
    +0x27  mov  [0xc0999c], esi

THIS PINS THREE THINGS AT ONCE. It is the fault instruction, byte for byte. It
shows the two calling conventions of section 7a in eleven instructions. And it
says what had to be true for the fault to happen at all: execution reached
+0x24, so data_0209f5bc was non-null AND its IsAtStart returned true, which
means the fault is on the NEW object and not on the installed one.

WHICH ALSO SETTLES WHICH SLOT THE AFTER RUN EXERCISES. hal/scene_boot.cpp
resets data_0209f5bc to 0 before the spawn, so dScMgBase_c slot 1's own
SetFaders is not the first: Scene::BeforeInitResources runs before it and
installs the gate-31 colour fader (a real HalFaderWipe at data_0209f5e8). By
the time slot 1 calls SetFaders the guard is true, IsAtStart answers true, and
+0x24 dispatches. The BEFORE binary died on that instruction; the AFTER binary
runs through it into +0x27 and on into InitResources. So slot 0x24 of this
seat IS dispatched, and that is the measurement rather than an inference from
the fill being present.

5. A DECOMP-SIDE DEFECT FOUND ON THE WAY: src/func_0202ed08.c

The ROM body at 0x0202ed08 is a bare tail-call veneer, three words:

    0202ed08  e59fc000  ldr ip, [pc]
    0202ed0c  e12fff1c  bx  ip
    0202ed10  0201761c  .word 0x0201761c   = _ZN15FaderBrightness8SetToEndEv

src spells it

    void func_0202ed08(void) { _ZN15FaderBrightness8SetToEndEv(); }

with no parameter and no argument. Under mwccarm that is byte-correct, because
`bx ip` leaves r0 alone and the receiver rides through. On the host the
receiver is simply gone. THIS IS THE SAME SHAPE lane LK4 wrote up for
_ZN4Heap8_DestroyEv in hal/lk4_solidheap_seat.cpp, and it is worth noting that
port/tools/closestplayer_guard.py -- which scans for exactly this -- passes on
it today, because the TU is not in any active slice.

Slot 0x20 therefore forwards to the veneer's own target with the receiver, and
src/func_0202ed08.c stays out of the link. Its sibling src/func_0202ecfc.c is
the same ROM shape and IS seated, because its C keeps the parameter.

THE DECOMP-SIDE FIX IS ROUTED, NOT TAKEN, the same way MG2 routed the
func_ov004_020b2cb8 template: the src TU should take a receiver and pass it,
and whether that still builds byte-identically under mwccarm is a
byte-gated-tree question. Seating the fixed TU and deleting the thunk's
forward is one commit.

THE MECHANISM, read out of the src rather than guessed. func_0205d714 is the
ROM's open-by-NAME entry: it copies the default archive record into the FSFile
(`out->field_8 = (int)t.field_0`, with `t = data_020a804c`) and hands it to
func_0205cdf4, whose second line is `char *list = *(char **)(self + 8)`
followed by `*(int *)(list + 0x10) & 0x80`. data_020a804c is zeroed host
storage -- hal/scene_boot.cpp:408 defines it as `int data_020a804c[3]` in a
block that reads it as "the Vram__Map family's LCDC cursor and its three-word
bank record". Its only ROM writer is func_0205cc80, the archive registration,
which nothing in the port runs. So field_0 is null and `list + 0x10` is 0x10.

WHY NOTHING HIT THIS BEFORE. Every other port file load goes through
hal/fs.cpp's ID-based seam. Open-by-name has had no caller until this scene.
Retiring it is a file-system job: either host the archive record for real, or
face func_0205d714 / func_02018e3c onto the seam hal/fs.cpp already owns. It is
not a fader, a minigame or a scene problem, and this lane did not take it.

The marker string battery.py pins the row on is printed by a successor
pre-flight added to hal/scene_mg.cpp, directly beside MG2's retired one. The
retired one is KEPT: it fires only when data_0209f61c[0] is zero, which is now
a regression assertion on this seat.


7. TWO HAZARDS THIS SEAT DOES NOT OWN, WRITTEN DOWN SO THEY ARE NOT REDISCOVERED

7a. TWO CALLING CONVENTIONS THROUGH ONE TABLE.
Scene::SetFaders touches a fader both ways in one function: `thiz->v24()` is a
local C++ class, __thiscall, receiver in ECX; `data_0209f5bc->vt->f14(
data_0209f5bc)` is a hand-written struct of function pointers, cdecl, receiver
on the stack. The second reaches whatever data_0209f5bc points at -- and after
the first SetFaders(data_0209f61c) that is this object.

Every thunk in the fill is __fastcall with two register parameters and NO stack
parameters, which is balanced for both shapes: a cdecl caller cleans its own
push, and a thiscall no-argument caller pushes nothing. That is a deliberate
difference from hal/fader_wipes.cpp, whose 0x0c and 0x10 stubs take two ints
and are therefore balanced for the cdecl shape only. What a cdecl entry still
costs is a GARBAGE RECEIVER, because the thunk reads ECX. That mismatch is not
new -- HalFaderWipe has carried it since it was written, and the pre-seat
reproduction went through it (f14 was called on hal_wipes[0] and returned true,
which is how v24 was reached at all). It belongs to whoever owns
Scene::SetFaders' host shape.

7b. THE MSVC DTOR FOLD, ONE SLOT EARLY.
The matched FaderBrightness::IsBetweenStartAndEnd ends in two UNQUALIFIED
IsAtStart()/IsAtEnd() calls, so it re-dispatches through the receiver's table.
mwcc puts those at ROM slots 5 and 6 (bytes 0x14, 0x18); MSVC folds the two
destructor slots into one, so the same calls compile to bytes 0x10 and 0x14 --
one slot early against a table kept in ROM byte order. hal/fader_wipes.cpp
names this and declines to delegate the method for exactly this reason.

It is reachable here only through func_0202ed7c's `type == 1` branch, and type
is the object's +0x14, which func_0202ed14 constructs as 0. It can be MADE 1:
func_ov004_020aeb24 calls func_0202ec9c(data_0209f61c, 1). It is NOT reached on
the scene-374 path, which is a measurement and not a guarantee, so the face in
hal/fdr_arm9_fader_seat.cpp prints when the receiver's type is 1 before
dispatching. With no stack parameters on the traps the skewed dispatch lands on
the 0x10 trap and the 0x14 IsAtStart thunk and comes back wrong-but-alive, and
both of them say so on stderr. Fixing it goes with the three motion slots.

9. UNPROVEN ITEMS

  * The three trap slots (0x08, 0x0c, 0x10) have never been dispatched. "They
    are not needed" is true of one 300-frame run of one scene and of nothing
    else. Any other minigame, and the level path's own fader use, may reach
    them.
  * OF THE SEVEN SEATED SLOTS, ONLY 0x24 IS PROVEN TO RUN. Section 2's
    disassembly is the proof for that one. 0x1c is NOT reached on this path:
    slot 1's `func_0202ec9c(data_0209f61c, 0)` takes its early return because
    the freshly constructed object's +0x14 is already 0, so the m1c dispatch
    never happens, and 0x14/0x18 are reached only from 0x1c. The two
    destructors, 0x00 and 0x04, are a separate case: they are linked and
    registered on data_020aa3f0's chain, nothing in the port walks that chain,
    and they are undriven for that reason rather than for want of a caller on
    this path. So the roster of the seven filled slots reads one PROVEN
    (0x24), two DESTRUCTORS (0x00, 0x04), and FOUR linked, reachable and
    unexercised (0x14, 0x18, 0x1c, 0x20). Six of the seven are not verified by
    anything here and this file will not call them verified.
  * The four ROM rulings in inferred_stub_adjudicated.txt are instruction-level
    comparisons of the ARM body against the src body. They say the src is a
    faithful decompilation; they do NOT say the compiled-for-host behaviour is
    identical, and for func_0202ed7c specifically 7b above is a case where it
    is not.
  * data_020a804c's identity is read from func_0205d714, func_0205cc80 and
    func_0205cbe4. hal/scene_boot.cpp's own comment reads it as a VRAM bank
    record instead. Both cannot be right and this lane did not settle which;
    the fault mechanism does not depend on the answer, but the fix does.
  * The dtor edge is linked but undriven. func_0202fc08 is registered on
    data_020aa3f0's chain by func_020731dc and nothing in the port walks that
    chain, so neither destructor has run in any measurement here.
  * The seat runs on three targets. Only walk_window has been RUN with it; the
    other two are link-and-battery evidence only.
