1. THE CLASS, AND THE ONE THING THE HANDOVER GOT WRONG

MG2's report, port/mg_fanout_costs.txt section 10 and battery.py's old
SCENE_BLOCKED row all describe data_0209f61c as "an arm9 FaderBrightness". It
is a dWipe_c. The ROM says so, in its own RTTI, with config/arm9/relocs.txt
applied to extracted/arm9_dec.bin (flat, base 0x02004000):

    0x020926dc  __si_class_type_info   name "7dWipe_c"           base 0x0208ea00
    0x0208ea00  __si_class_type_info   name "10dFdColor_c"       base 0x0208ea24
    0x0208ea24  __si_class_type_info   name "15dFdBrightness_c"  base 0x0208e9e0
    0x0208e9e0  __class_type_info      name "8dFader_c"
    0x0208ea18  __si_class_type_info   name "9dFdWipe_c"         base 0x0208ea00

    dFader_c <- dFdBrightness_c <- dFdColor_c <- dWipe_c

which is exactly the four vptr stores func_0202fc40 makes, in base-to-derived
construction order, and which also identifies the three sibling tables the port
already hosts by number rather than by name:

    data_0208eafc = _ZTV8dFader_c            hal/scene_boot.cpp:702, ROM bytes
    data_0208eacc = _ZTV15dFdBrightness_c    hal/scene_boot.cpp:693, trap-filled
    data_0208eb2c = _ZTV10dFdColor_c         hal/scene_boot.cpp:688, trap-filled
    _ZTV9FaderWipe (config name) = _ZTV9dFdWipe_c, 0x0208ea9c

NOTHING IN THE HANDOVER'S CONCLUSIONS CHANGES. Every address MG2 gave is right,
including the one that matters most ("a host fill for data_020926f0, which is
NOT _ZTV9FaderWipe"). What changes is what a successor searches for: a lane
told "FaderBrightness" goes looking in the 0x02017xxx fader engine, and none of
the ten bodies is there.

WHY 0x24, off the compiled binary rather than off the C. src/_ZN5Scene9SetFaders
EP15FaderBrightness.cpp declares a local `struct Scene` with ten virtuals and
calls thiz->v24(); MSVC puts that at byte 0x24, which under the ROM fader slot
order is SetToStart. The first 0x27 bytes of the host function, disassembled
out of walk_window.exe:

    +0x00  push ebp / mov ebp,esp
    +0x03  mov  ecx, [0xc0999c]           data_0209f5bc, the INSTALLED fader
    +0x09  test ecx,ecx / je +0x74        the ROM's own null guard
    +0x0d  mov  eax, [ecx]                its vptr
    +0x0f  push esi                       the callee-save, NOT an argument
    +0x10  push ecx                       CDECL: receiver on the stack
    +0x11  mov  eax, [eax + 0x14]         IsAtStart, by ROM byte offset
    +0x14  call eax
    +0x19  test eax,eax / je +0x36
    +0x1d  mov  esi, [ebp + 8]            thiz, the NEW fader
    +0x20  mov  ecx, esi                  THISCALL: receiver in ECX
    +0x22  mov  eax, [esi]                its vptr
    +0x24  call dword ptr [eax + 0x24]    SetToStart
    +0x27  mov  [0xc0999c], esi

THIS PINS THREE THINGS AT ONCE. It is the fault instruction, byte for byte. It
shows the two calling conventions of section 7a in eleven instructions. And it
says what had to be true for the fault to happen at all: execution reached
+0x24, so data_0209f5bc was non-null AND its IsAtStart returned true, which
means the fault is on the NEW object and not on the installed one.

WHICH ALSO SETTLES WHICH SLOT THE AFTER RUN EXERCISES. hal/scene_boot.cpp
resets data_0209f5bc to 0 before the spawn, so dScMgBase_c slot 1's own
SetFaders is not the first: Scene::BeforeInitResources runs before it and
installs the gate-31 colour fader (a real HalFaderWipe at data_0209f5e8). By
the time slot 1 calls SetFaders the guard is true, IsAtStart answers true, and
+0x24 dispatches. The BEFORE binary died on that instruction; the AFTER binary
runs through it into +0x27 and on into InitResources. So slot 0x24 of this
seat IS dispatched, and that is the measurement rather than an inference from
the fill being present.

4a. SLOT 0x08 IS STILL A TRAP, AND THAT IS A RULING.

func_0202f428 was disassembled and ruled REAL_DECOMP with the other two
(port/tools/inferred_stub_adjudicated.txt). It is not seated, for two reasons
that hold together and would not hold apart.

THE SRC TU IS HOST-BROKEN in exactly the way section 5 describes for
src/func_0202ed08.c. Its `type == 1` branch is

    0202f440  bl  0x020174e0        _ZN10FaderColor11AdvanceFadeEv

with no `mov r0, r4` in front of it, because on ARM r0 still holds the
receiver from entry. src spells that as `_ZN10FaderColor11AdvanceFadeEv()` and
include/decl_FaderColor.h declares it `(void)`, so the call is not even a
warning -- and on the host the receiver is gone. Unlike slot 0x20, the broken
call is INSIDE a larger body rather than being the whole of it, so there is no
veneer to route around: seating the body means shipping the call.

AND THERE IS NOTHING TO BUY. Slot 0x08 has NO CALL SITE in this image; section
9a enumerates them and explains why the port's own fade driver
(hal/fader_wipes.cpp:port_fader_advance, which dispatches 0x08 on
data_0209d4b0[0]) cannot reach this object: nothing writes it there.
func_0202f58c does not, and the only writers in the link write a different
fader. So the slot would be a linked, undriven body carrying a receiver-
dropping call.

THE REFUSAL IS NOW MECHANICAL RATHER THAN WRITTEN DOWN.
port/tools/closestplayer_guard.py carries a rule for
_ZN10FaderColor11AdvanceFadeEv, so the day someone puts src/func_0202f428.c in
a slice the build stops with the remedy printed. The guard passes today
because the TU is in no slice, which is the same state it reports for
func_0202ed08.

WHAT THE MOTION SEATS DO AND DO NOT MAKE HAPPEN. The two setters now run for
real on scene 374 -- they write the eight blend registers, build both halves of
the scanline table and install the ROM's HBlank handler. THE FADE STILL DOES
NOT MOVE, and the reason is not this table: the motion comes from IRQ 2, which
nothing on the host raises, and from AdvanceFade, which nothing calls. That is
in the unproven items rather than in this paragraph's conclusion, because it is
a statement about today's host and not about the class.

src/func_0202ed08.c stays out of the link. Its sibling src/func_0202ecfc.c is
the same ROM shape and IS seated, because its C keeps the parameter.

THE MECHANISM, read out of the src rather than guessed. func_0205d714 is the
ROM's open-by-NAME entry: it copies the default archive record into the FSFile
(`out->field_8 = (int)t.field_0`, with `t = data_020a804c`) and hands it to
func_0205cdf4, whose second line is `char *list = *(char **)(self + 8)`
followed by `*(int *)(list + 0x10) & 0x80`. data_020a804c is zeroed host
storage -- hal/scene_boot.cpp:408 defines it as `int data_020a804c[3]` in a
block that reads it as "the Vram__Map family's LCDC cursor and its three-word
bank record". Its only ROM writer is func_0205cc80, the archive registration,
which nothing in the port runs. So field_0 is null and `list + 0x10` is 0x10.

WHY NOTHING HIT THIS BEFORE. Every other port file load goes through
hal/fs.cpp's ID-based seam. Open-by-name has had no caller until this scene.
Retiring it is a file-system job: either host the archive record for real, or
face func_0205d714 / func_02018e3c onto the seam hal/fs.cpp already owns. It is
not a fader, a minigame or a scene problem, and this lane did not take it.

The marker string battery.py pins the row on is printed by a successor
pre-flight added to hal/scene_mg.cpp, directly beside MG2's retired one. The
retired one is KEPT: it fires only when data_0209f61c[0] is zero, which is now
a regression assertion on this seat.

7a. TWO CALLING CONVENTIONS THROUGH ONE TABLE.
[REFUTED, AND NOW REPLACED. Run link60 lane FDR2 enumerated every dispatch site
in the image and found THREE caller shapes rather than two; the fill's twelve
signatures were re-declared against the measurement and the crash below is

[REFUTED IN PART, run link60 lane NFS, coordinator note. The paragraph below
argues the fill's no-stack-parameter __fastcall thunks are balanced for both
caller shapes. Scene 374's first behaviour tick FALSIFIED that for the pushed-
argument case: Scene::BeforeBehavior pushes 0 and 0x1E into [vt+0x0c] and
cleans NOTHING after the call, so the fastcall stub leaks eight bytes and ret
lands on the caller's saved esi. Slot 0x10 carries the identical defect on its
branch. The instruction-level mechanism, register file and fix shape are in
port/nfs_names_map.txt section 7; the fix (ABI-correct stubs or ROM bodies for
0x0c and 0x10 plus an audit of all twelve stub signatures) belongs to the seat
this file documents. Read the paragraph below as the design intent that was
refuted, kept for the record.]
Scene::SetFaders touches a fader both ways in one function: `thiz->v24()` is a
local C++ class, __thiscall, receiver in ECX; `data_0209f5bc->vt->f14(
data_0209f5bc)` is a hand-written struct of function pointers, cdecl, receiver
on the stack. The second reaches whatever data_0209f5bc points at -- and after
the first SetFaders(data_0209f61c) that is this object.

Every thunk in the fill is __fastcall with two register parameters and NO stack
parameters, which is balanced for both shapes: a cdecl caller cleans its own
push, and a thiscall no-argument caller pushes nothing. That is a deliberate
difference from hal/fader_wipes.cpp, whose 0x0c and 0x10 stubs take two ints
and are therefore balanced for the cdecl shape only. What a cdecl entry still
costs is a GARBAGE RECEIVER, because the thunk reads ECX. That mismatch is not
new -- HalFaderWipe has carried it since it was written, and the pre-seat
reproduction went through it (f14 was called on hal_wipes[0] and returned true,
which is how v24 was reached at all). It belongs to whoever owns
Scene::SetFaders' host shape.

7b. THE MSVC DTOR FOLD, ONE SLOT EARLY.
The matched FaderBrightness::IsBetweenStartAndEnd ends in two UNQUALIFIED
IsAtStart()/IsAtEnd() calls, so it re-dispatches through the receiver's table.
mwcc puts those at ROM slots 5 and 6 (bytes 0x14, 0x18); MSVC folds the two
destructor slots into one, so the same calls compile to bytes 0x10 and 0x14 --
one slot early against a table kept in ROM byte order. hal/fader_wipes.cpp
names this and declines to delegate the method for exactly this reason.

It is reachable here only through func_0202ed7c's `type == 1` branch, and type
is the object's +0x14, which func_0202ed14 constructs as 0. It can be MADE 1:
func_ov004_020aeb24 calls func_0202ec9c(data_0209f61c, 1). It is NOT reached on
the scene-374 path, which is a measurement and not a guarantee, so the face in
hal/fdr_arm9_fader_seat.cpp prints when the receiver's type is 1 before
dispatching. With no stack parameters on the traps the skewed dispatch lands on
the 0x10 trap and the 0x14 IsAtStart thunk and comes back wrong-but-alive, and
both of them say so on stderr. Fixing it goes with the three motion slots.

9. THE TWELVE STUB SIGNATURES, AUDITED AGAINST EVERY CALLER

Run link60 lane FDR2, worktree C:/tmp/f2, branch s4-fdr2-motion, off 34d3a3130.
This is the audit port/nfs_names_map.txt section 7 asked for and the answer to
7a above. It is measured on THIS LANE'S OWN walk_window.exe: every address in
it was disassembled out of that binary, and none of NFS's addresses is quoted,
because the two builds do not share a layout.

9a. HOW THE SITES WERE FOUND, so the enumeration can be checked rather than
believed. Three passes, because no one of them is complete:

  * MECHANICAL. Every function in walk_window.map's .text was disassembled and
    swept for the pattern "load the object out of a watched global, load its
    vptr, call through a slot of it". The watched globals were data_0209f5bc
    (the INSTALLED fader), data_0209f61c (the object), data_020926f0 (the table
    itself), and data_0209d4ac and data_0209d4b0, which Scene::SetFaders and
    the fade driver also point at faders. Fifteen sites.

    AND THE SWEEP HAS A BLIND SPOT, WHICH IT COST ONE SITE TO FIND. It is a
    LINEAR disassembly carrying per-register state, so it loses a vptr across a
    conditional branch: a call at a JUMP TARGET, whose vptr was loaded before
    the jump and whose register the fall-through path overwrote in between, is
    invisible to it. Scene::BeforeBehavior+0xd4 is exactly that shape -- the
    vptr is loaded at +0x53, the `je` at +0x55 skips forward, and the
    fall-through writes EAX twice before the target is reached -- and the sweep
    did not report it. Review found it. It is in 9c now, and the sweep's output
    should be read as a floor rather than as an enumeration.
  * BY ADDRESS, the pass that closes that gap. Every function above was
    re-disassembled whole and EVERY `call dword ptr [reg + imm]` in it listed,
    with no state tracking to lose, and each one's receiver read by hand. That
    is what reconciles: slot 0x14's nine, slot 0x18's four, and the calls that
    look like this table's and are not -- ProcessKuppaScript's other seven

9b. THE THREE SHAPES MSVC EMITS, and the cleanup each one requires. The
distinction that matters is not cdecl-versus-thiscall, it is WHO CLEANS:

  A  THISCALL, no arguments      mov ecx,<obj> / call [vt+off]
                                 nothing pushed; callee must clean 0
  B  THISCALL, two arguments     push b / push a / mov ecx,<obj> /
                                 call [vt+off], and NO cleanup follows
                                 8 bytes pushed; callee must clean 8
  C  CDECL, struct of pointers   push <obj> / call eax / add esp,4
                                 caller cleans its own push; callee cleans 0

Shape B is the one 7a did not enumerate, and it is the crash. Shapes A and C
agree on the cleanup and differ only on where the receiver is, which is a wrong
`this` and not a smashed frame.

TWO SIGNATURES CHANGED, 0x0c and 0x10, and the other ten were CONFIRMED rather
than left alone. __fastcall(self, edx, a, b) is the host spelling of
__thiscall(self, a, b): the receiver arrives in ECX, EDX is unread, a and b come
off the stack, and MSVC emits `ret 8`. THE ARITY IS THE CALL SITE'S AND NOT THE
ROM BODY'S -- func_0202f708 takes only (self, frames), because on ARM the third
argument rides in r2 and costs nothing, but the host caller pushed two words and
the stub has to clean two words. A stub sized to the ROM body would leak four.

9e. THE ONE SLOT NO SIGNATURE COULD SERVE, and what was done about it.
Slot 0x10 is reached by shape B from Scene::BeforeBehavior and by shape A from
the matched IsBetweenStartAndEnd. Declared for B it smashes eight bytes off A's
frame; declared for A it leaks eight on B, which is the crash this lane was
sent to fix. There is no third option in C.

The A site was removed. hal/fdr_arm9_fader_seat.cpp's
_ZN15FaderBrightness20IsBetweenStartAndEndEv no longer delegates to the matched
method; it dispatches the RECEIVER'S OWN 0x14 and 0x18, which is the pair the
ROM's two virtual calls reach, and keeps the matched body's arithmetic. That is
hal/fader_wipes.cpp's existing ruling on this method applied to the one place
that had not taken it, and it retires 7b's "wrong-but-alive" answer as a side
effect rather than as a separate fix. The matched TU stays in the link and stays
counted; nothing calls it now, and that is written into the unproven items.
