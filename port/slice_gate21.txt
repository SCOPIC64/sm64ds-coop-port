# Gate 21: ov100's BUTTERFLY and FISH.
#
# The port's third actor overlay. ov100 carries seven classes -- BUTTERFLY,
# ROLLING_IRON_BALL, UNCHAINED_CHOMP, DOOR, STAR_DOOR, FISH and PATH_LIFT --
# and the castle grounds names three of them. Two here; the door is gate 22,
# because its own Behavior and Render each need a host copy and its
# InitResources reaches into a fourth overlay.
#
# THE CONFIG'S NAMES ARE MOSTLY RIGHT IN ov100 AND EXACTLY ONE PAIR IS
# SHIFTED, which is why every one was checked. Each factory's literal pool
# names the vtable it installs and the ROM's RTTI names it back:
#
#   Butterfly_Spawn 0x02141ea4 -> _ZTV9Butterfly      RTTI 9daBtfly_c   OK
#   Fish_Spawn      0x02146d38 -> _ZTV4Fish           RTTI 8daFish_c    OK
#   Door_Spawn      0x0214589c -> data_ov100_02148188 RTTI 8daDoor_c    UNNAMED
#   StarDoor_Spawn  0x021461d4 -> _ZTV4Door           RTTI 12daStarGate_c
#
# So config's `_ZTV4Door` is the STAR door's table and the whole _ZN4Door*
# method family implements the star door; the real door (actor 353) is the
# unnamed func_ov100_* family. Gate 22 uses those; nothing is renamed.
#
# The mount is port/ov100_syms.txt -- and it is the first that has to exclude
# a vtable BY ADDRESS, because the "_ZTV*" rule cannot see one dsd left as
# data_ov100_*. See that file's header.

# ---- FISH (actor 344, ov100) x2 -------------------------------------------
# The two shoals in the moat. Seven states, and the class is bound to a PARENT
# ACTOR rather than to a position: Behavior looks its owner up by id every
# frame (Actor::FindWithID on +0x13c) and marks itself for destruction if the
# owner is gone or refuses it, which is how a shoal follows the water it was
# spawned against.
#
# _ZN4Fish8BehaviorEv IS NOT HERE: it dispatches an mwcc pointer-to-member out

# case for the fifth time, so MSVC would quadruple the stride. Host copy plus
# the seven-static seat in port/unmatched/Fish_Behavior.cpp. All seven states
