THE PORT'S ABI DEFECT CHECKERS
==============================

What this file is: the evidence for port/tools/aliascheck.py, abicheck.py,
aritycheck.py, abi_prove.py and run_checks.py. What each one asserts, the
commands that show each one GREEN on this tree and RED on a deliberately
re-broken copy of it, the fixture inventory, the live defects the suite found
on cons the day it landed, and the drift that had to be resolved to get here.

A reviewer should be able to re-run every proof in this file from this file
alone. If a command below does not reproduce, the checker is wrong, the tree
moved, or this document is stale, and all three are worth knowing.

Written 2026-08-17, run link60 lane AB1, on cons port-mount-noseat-cluster
3a5733c03. AMENDED the same day after lane ABR1's review, which rebuilt the
tree, re-derived every number, confirmed all six live defects from its own
disassembly, and found two things this document had asserted and got wrong:
that undname was unavailable (it was an invocation bug, section 5 item (j)),
and that the sixth defect was already on aritycheck's census (it was not,
item (k)). Both are fixed in the tools rather than only in the prose, and both
are left written down. Every number below is from a run after those fixes.


0. WHY THIS EXISTS, AND WHY IT IS A RECOVERY
--------------------------------------------

There is one defect class the PC port keeps producing. It has three source
shapes and one mechanism: THE RECEIVER IS DELIVERED SOMEWHERE THE BODY DOES
NOT READ IT.

On ARM a C++ member's `this` rides r0, exactly like any other first argument,
so a ROM body transcribed into C takes it as an ordinary parameter. On x86
MSVC the same method compiled as C++ is __thiscall and takes it in ECX. Any
seam between those two worlds that does not name the receiver loses it, and
nothing warns:

  * an /alternatename directive whose two sides disagree (aliascheck)
  * a declaration that says (void) where the definition takes a receiver
    (aritycheck)
  * a vtable thunk whose emitted `ret` does not match the pop its slot demands
    (abicheck)

The class is not theoretical and it is not closed. It produced 11 of the 60
stored player crash reports as one family (blendmodelanim-setanim-abi-bridge),
and on 2026-08-16 alone it produced six separate receiver fixes on cons.

The checkers themselves are a RECOVERY. They were written 2026-08-10 on two
branches, port-abi-sweep (b472454c6, seven commits) and port-defect-wiring
(4ec689079, two commits), proven at the time, held pending a merge that
cleared on 2026-08-11, and then forgotten for six days while the class they
guard recurred six more times. Section 5 is the list of what had drifted.


1. WHAT EACH CHECKER ASSERTS
----------------------------

aliascheck.py -- no build required
  RULE R, receiver location. An /alternatename renames a symbol and says
  nothing about calling convention. Classify each side of every directive as
  taking its receiver in ECX (a non-static member declared __thiscall or
  __fastcall; the extern "C" @name@N spelling) or on the stack (everything
  else: a free function, a static member, a flat extern "C" name, a member
  declared __cdecl or __stdcall). ASSERT the two sides agree.
      DROPPED  stack left, ECX right. The caller pushes the receiver; the body
               reads ECX and gets whatever was in it.
      SHIFTED  ECX left, stack right. The caller sets ECX; the body reads its
               first stack slot, which holds the caller's first pushed
               argument or, if nothing was pushed, the return address. Every
               declared argument shifts by one on top of that.
  Decided from the decoration alone: no build, no demangler, no external tool.
  RULE R fires the moment a bad alias is written.

  RULE P, pop size. Both sides' callee-pop from their declared parameter
  lists. Needs `undname` to read an MSVC parameter list. WHEN undname IS
  ABSENT RULE P DOES NOT RUN AND SAYS SO. Rule R is complete without it.

  THIS RULE SPENT ITS FIRST DAY REPORTING "undname is not on PATH" ON A
  MACHINE WHERE undname WAS INSTALLED AND WORKING, and the first version of
  this document repeated that as an environment limit. It was not an
  environment limit, it was an invocation bug. undname takes FILENAMES:

      Usage: undname [flags] fname [fname...]
         or: undname [flags] file

  The helper piped the name list into its stdin, undname answered with that
  usage banner and exit 1, and the helper read the non-zero exit as "the tool
  is missing". Lane ABR1 caught it in review. Verified here afterwards, both
  directions, at
  ...\VC\Tools\MSVC\14.44.35207\bin\Hostx86\x86\undname.exe: the file form
  returns one bare demangled line per input line and exit 0; the stdin form
  returns the banner and exit 1. Demangling now lives in
  port/tools/msvc_undname.py, which finds undname on PATH or under the VS
  Build Tools layout, uses the file form, and has a selftest that pins both
  the known-good output and the fact that stdin is refused. Rule P runs.

  GATE: a receiver crossing that is not in port/tools/aliascheck_baseline.txt
  fails. Every baseline row carries an OPEN or INERT adjudication and an
  UNADJUDICATED row is reported as a defect of the baseline itself.

abicheck.py -- needs a build and dumpbin /disasm:nobytes
  A hosted virtual slot is entered as __thiscall: `this` in ECX, further
  arguments PUSHED, and the CALLEE pops them. A __fastcall thunk pops nothing
  unless it declares enough parameters to put the pushed ones on the stack,
  which is what makes the compiler emit `ret <n>`. ASSERT that for every
  vtable slot fill, the thunk's emitted `ret` equals 4 times the argument
  count its slot demands. Both halves are read from the emitted code: the slot
  from the fill's own store offset, the pop from the terminating ret.
      AUTHORITY  slot -> argument count from include/ActorBase.h (0..17) and
                 include/Actor.h (18..30).
      CONSENSUS  no header at all: a thunk whose pop disagrees with its peers
                 at the same slot index across every Actor table is suspect.
                 This is what covers the non-Actor tables and a slot whose
                 header authority is wrong.
  Two exemptions, both mechanical: a thunk whose every path funnels into
  port_actor_slot_decline / abort / RaiseException never reaches its own ret
  (DECLINE), and a table that is not the 31-slot Actor layout has a different
  slot map (NO_AUTHORITY, consensus only).
  GATE: exit 1 on any AUTHORITY mismatch or CONSENSUS outlier; exit 2 on a run
  that parsed ZERO slot fills, which is what plain /disasm produces.

aritycheck.py -- no build required
  The linker matches extern "C" symbols on the NAME alone, so a declaration
  and a definition can disagree about arity and nothing complains. ASSERT they
  agree.
      DROPS    the declaration has FEWER parameters. The callee reads a stack
               slot the caller never wrote.
      INVENTS  the declaration has MORE. Under __cdecl the caller cleans up,
               so the extra push is wasted rather than fatal.
  THE FULL CENSUS DOES NOT GATE. It reports 2105 disagreements on this tree
  and an unknown but large fraction are parser artefacts; a gate at that
  number would be switched off within a day. Section 7 says what would have to
  change.
  ONE SUBSET GATES: the RECEIVER SHAPE, a declaration with no parameters at
  all against a definition of an Itanium-mangled member (_ZN...) that takes at
  least one. 168 live rows are frozen in
  port/tools/aritycheck_receiver_baseline.txt and a NEW one fails
  --gate-receiver. That subset is exactly what PR #1539 and PR #1543 fixed on
  2026-08-16, and it is where the sixth live defect of section 6 surfaced once
  the reader learned the namespaced C++ declaration spelling.

vtspan.py --sweep / --fills -- needs the extracted ROM, ALREADY ON CONS
  Not recovered by this lane; cons' own copy is used unchanged, and nothing in
  this change touches it. --sweep finds a host vtable array shorter than its
  ROM span; --fills finds a fill loop that leaves a ROM slot unwritten.
  run_checks fires both against ratchet files this lane wrote:
    vtspan_sweep_baseline.txt   EMPTY. Four tables were short when the wiring
        was written on 2026-08-10; the sizing lanes finished and cons measures
        0 short. --sweep therefore gates hard.
    vtspan_fills_baseline.txt   6 frozen fills (4 that leave slots unwritten,
        2 the scan cannot resolve to a ROM table at all). All pre-existing on
        cons. A gate that is red the day it lands is a gate somebody switches
        off, so these are frozen, counted on every run, and the list may only
        shrink. They are DEBT, not clearance -- nobody adjudicated them here.

run_checks.py -- the one command
  Fires the set and fails on any red AND on any vacuous pass. Its own
  contribution is stage 0: every checker's --selftest must pass before any of
  them is believed, because a regex that stopped matching a shape reports a
  clean tree in exactly the same words as a clean tree.

3. RED ON DEMAND -- THE PROOF HARNESS
-------------------------------------

A checker that only ever passes has proved nothing. abi_prove.py runs both
halves for every fixture:

    GREEN  the checker passes on the tree as it stands, AND the fixture's own
           defect is verified gone from it
    RED    the fixture is re-broken IN A SCRATCH COPY and the checker must
           fail, naming it

    PASS aliascheck RED: Heap::Destroy
    PASS aliascheck RED: Heap::_Destroy

    PASS aliascheck RED: SolidHeapAllocator::Reallocate
    PASS aliascheck RED: Player::TryGrab
    PASS aliascheck RED: BlendModelAnim::SetAnim
    PASS aliascheck RED: Platform::KillByMegaChar
    PASS aliascheck RED: a pop mismatch RULE R cannot see (rule P only)
    PASS aritycheck GREEN on cons
    PASS aritycheck RED: FaderColor::AdvanceFade
    PASS aritycheck RED: Enemy base ctor
    PASS aritycheck RED: namespaced C++ declaration
    PASS aritycheck GREEN again once the fixture is removed
    PASS abicheck GREEN on this build
    PASS abicheck RED: crate_pounded

    PASS abicheck RED: whomp_s30
    23 of 23 proofs passed
    ABI_PROVE PASSED

  Without --disasm-dir the abicheck arm is SKIPPED and the harness FAILS
  (16 of 17, "abicheck arm ran at all: FAIL"), rather than reporting a pass
  over a checker it never ran. That is the vacuous-green rule applied to the
  proof harness itself. Measured, because the first version of this document
  guessed at that number and guessed wrong.

  EACH RED ASSERTS WHICH RULE FIRED, not merely that the checker exited 1.
  The first version asked for the substring "NEW", which appears in
  aliascheck's own count line on every run including a clean one, so it was
  very nearly no assertion at all. The rule-P fixture is the one that made
  that matter: it is a pop mismatch with both sides __thiscall, so the
  receiver rule is CORRECT to stay quiet and only "POP MISMATCH" in the
  output proves rule P did the catching.

THE SCRATCH COPY IS A COPY. The real tree is never edited, not even
transiently, so an interrupted run cannot leave a re-broken directive behind.
The harness also REFUSES to start if port/hal/abi_prove_reinjected.cpp exists
in the real tree, which is the only file it ever writes.

How each arm is re-broken:
  aliascheck   the deleted directive is written back as a real
               `#pragma comment(linker, "/alternatename:...")` in a new file
               under the scratch copy's port/hal/, which is exactly how a real
               one arrives.
  aritycheck   the real declaration is rewritten to its pre-fix (void)
               spelling by literal reverse substitution. If the FIXED text is
               no longer in the file the fixture REFUSES rather than silently
               proving nothing.
  abicheck     a scratch copy of the REAL disassembly of this build has one
               thunk's `ret <n>` rewritten to a bare `ret`. That is precisely
               the emitted shape of the bug -- crate_pounded shipped exactly
               like this -- so the proof runs against real input.

5. THE DRIFT, AND HOW IT WAS RESOLVED
-------------------------------------

Six days of tree movement. Every resolution is in favour of what is on cons.

(a) THE SHARED SCRATCH DIRECTORY. Both recovered tools read and wrote a fixed
    absolute path, C:\tmp\sm64ds-abisweep\. abicheck's input directory was a
    module-level constant, run_checks guarded that same constant on purpose
    because it could not pass abicheck a directory, and gen_disasm.cmd wrote
    there. Two lanes running the suite at once would have written each other's
    disassembly and each measured the other's build, and both would have read
    green. RESOLVED: abicheck requires --disasm-dir and has no default;
    gen_disasm.cmd takes an out-dir and defaults it inside the build
    directory; the CMake target passes ${CMAKE_BINARY_DIR}/_abicheck_disasm.

(b) THE SCANNER READ LANE PROSE AS LINKER INPUT. aliascheck walked the tree
    with its own regex and counted every /alternatename it saw. On this tree
    that reports 1590 directives where 1573 are real linker input and 17 are
    quotations in comments and .txt maps -- and THREE of those 17 are
    quotations of exactly the receiver-crossing directives the 2026-08-16
    fixes DELETED, sitting in the comment blocks that record the fix. The
    checker would have reported a defect out of the note saying it was fixed.

    THREE, not the five this document first claimed. All 17 prose lines were
    put through aliascheck.crossing() and the crossings are
    stage_lifecycle_map.txt:1084 and hal/stage_slot0.cpp:480, both quoting
    Heap::SetDefault, and hal/scene_boot.cpp:1176 quoting
    ModelComponents::Render. A fourth, CMakeLists.txt:3252, is a truncated
    regex over the Render directive and does not classify as a crossing. The
    remaining thirteen are data and vtable bridges. Lane ABR1 found the
    miscount; it was re-derived here rather than taken on report.
    Cons already solved this: commit ab554f5fd taught alternatename_guard.py
    the difference, after the same mistake failed a build over a comment.
    RESOLVED: aliascheck no longer walks the tree. It calls
    alternatename_guard.collect_directives(), and the selftest pins the
    distinction.

(c) THE POP RULE COULD NOT SEE THE SHAPE THAT ACTUALLY RECURS. The recovered
    aliascheck decided everything by comparing POP SIZE. A zero-argument
    __thiscall method pops 0; a flat extern "C" cdecl name pops 0; they match,
    and the checker says OK. Heap::SetDefault is ?SetDefault@Heap@@QAEHXZ --
    no arguments. So the recovered checker could NOT have caught the defect
    that cost a measured fault the day before this lane ran, nor
    Heap::Destroy, Heap::ResizeToFit, HeapAllocator::Remove or
    Player::GetHurtState. It caught TryGrab, SetAnim and KillByMegaChar only
    because those three happen to take an argument. RESOLVED: the primary rule
    is now RECEIVER LOCATION, which subsumes all three original fixtures and
    catches the zero-argument ones; pop size is kept as a secondary rule.

(d) THE PROOF WENT RED WHEN THE BUGS WERE FIXED. prove.py asserted that all
    nine known instances were CAUGHT on its tree, which worked only because
    its worktree predated every fix. All nine are fixed now, so the original
    fails on cons -- not a regression, a snapshot. RESOLVED: inverted, per
    section 3.

(e) vtspan.py. port-defect-wiring carried its own NEW copy of vtspan.py (806
    lines) from a feature branch, and reconciling with B's canonical copy was
    the named landing prerequisite on 2026-08-10. Cons now has vtspan.py
    (1041 lines) with all three modes the wiring needs (--sweep, --fills,
    --seats). RESOLVED: the wiring branch's copy is DROPPED entirely; cons'
    is used unchanged and nothing in this change touches it.

(f) THE ALTERNATENAME SURFACE MOVED. Six receiver bridges landed 2026-08-16
    and deleted six of the directives the original tools were written against,
    and the caller displacements of lanes RT1/AE1/TS1 retired tail-jump rows.
    RESOLVED: the fixture set is rebuilt from the actual deleted directives,
    read out of the fixing commits rather than from the six-day-old list, and
    the baseline is a census of what is live TODAY.

(g) aritycheck's SCAN MISSED HEADERS. It walked src/, port/unmatched/ and
    port/hal/ for .c and .cpp only. PR #1539's defect was in
    include/decl_FaderColor.h, so the recovered checker would not have caught
    the more recent of its own two best instances. RESOLVED: include/ is
    scanned and .h files are read. That moved the census from 2005 to 2104 and
    the receiver subset from 162 to 167, which is a cheap way to buy the
    surface where a real recurrence actually happened. A second reader gap of
    the same kind, the namespaced C++ declaration spelling, was found later by
    lane ABR1's review and is item (j).

(h) gen_disasm.cmd WAS UNUSABLY SLOW. `for /r` over the whole build directory
    visits every one of the port's fourteen thousand objects and filters each
    through a piped findstr. Measured here: still running after ten minutes,
    with cmd.exe past 2.3 GB. RESOLVED: it enumerates
    <build>\CMakeFiles\*.dir\hal\*.obj directly. 477 objects in 2m27s.

(i) veneercheck.py IS NOT LANDED, AND THAT IS A MEASUREMENT. Its rule was "a
    call to an Itanium member name written with ZERO arguments always drops
    `this`". On this tree that fires 686 times, and the premise is false: many
    matched src bodies genuinely take no receiver, because the ROM body never
    reads r0. src/_ZN4Tree8BehaviorEv.cpp is `int _ZN4Tree8BehaviorEv(void)`
    and walks a global list, so the thunk at hal/actor_classes.cpp:439 calling
    it with nothing is CORRECT. The sound version of that rule is arity
    agreement between declaration and definition, which is aritycheck. Landing
    veneercheck would have added 686 false positives to a suite whose whole
    value is that its reds are real. Lane ABR1 re-checked the exclusion on
    three of the 686 and agreed.

THE LAST TWO ITEMS ARE NOT DRIFT FROM THE OLD BRANCHES. They are defects this
lane introduced or carried, found by lane ABR1's review of this very change,
and they are recorded beside the rest because a recovery that hides its own
review findings is the same failure the recovery was for.

(j) THE DEMANGLER WAS NEVER CALLED CORRECTLY, so two capabilities read as
    blocked external dependencies for a day. aliascheck's helper piped its
    name list into undname's stdin; undname takes FILENAMES and answers a pipe
    with its usage banner and exit 1; the helper read that exit as "the tool
    is missing". Consequences, both of which this document asserted as
    environment limits:
      * aliascheck RULE P reported NOT RUN in every environment.
      * abicheck fell back to a precomputed _unres.txt / _unres_demangled.txt
        pair that nothing has ever generated, so extsig was always empty and
        638 of 2391 fills read NORETURN -- UNCHECKED, and reported as a
        coverage limit of the machine rather than of the code.
    RESOLVED: port/tools/msvc_undname.py, one caller, the FILE form, a locator
    that also finds undname under the VS Build Tools layout so a plain shell

7. LIMITS, STATED
-----------------

  * abicheck judges 47% of the fills it reads. The 132 NORETURN are
    UNCHECKED, not passed. They are thunks whose tail-jump target is a flat
    Itanium body carrying no parameter list in its spelling, so no demangler
    closes them; the fix is to read the pop out of the target's own emitted
    `ret`, which means disassembling beyond the hal objects.
  * aritycheck's full census (2105 rows) does not gate and its parser is a
    regex over C and C++ text. The honest route to gating it is to read arity
    out of the emitted code -- the callers' push counts, the way abicheck
    reads emitted rets -- not a bigger regex.
  * aritycheck reads ONE C++ declaration spelling beyond the flat names:
    `namespace X { T f(); }`, single level, no arguments. Templates, nested
    namespaces, overloads, arguments and out-of-line class methods are not
    attempted. Each of those is a place a call site can hide the way
    src/func_ov007_020b7764.cpp did for six days.
  * The 168 frozen receiver-shape rows, the 11 INERT crossings and the 6
    frozen vtspan fills are DEBT. The ratchets' claim is deliberately narrow
    and true: the tree does not grow a new one without somebody seeing it.
  * aliascheck reads the DIRECTIVE, not the call sites. It says a crossing
    exists; whether the crossing bites depends on what the callers do, which
    is why every baseline row carries a hand adjudication rather than a
    verdict the tool computed. The sixth defect is the standing proof that a
    checker reading one artefact can be blind to the site that matters.
  * Nothing here runs automatically. Section 8.

8. WHAT IS WIRED, AND WHAT IS ONLY PROPOSED
-------------------------------------------

WIRED (opt-in, nothing changes for anyone who does not type it):

    ninja -C build/port port_checks_nobuild   the four no-build checkers
    ninja -C build/port port_checks           + abicheck over THIS build
    ninja -C build/port port_abi_prove        the green/red proof harness

  NEITHER port_checks TARGET IS IN ALL, and that is deliberate. The recovered
  CMake wiring put port_checks in ALL on MSVC. The port has no CI, so a target
  in ALL is the only thing that would run these for other people -- and
  turning a currently-green build red for every contributor is the port
  owner's decision, not a recovering lane's. build-port.cmd is untouched for
  the same reason, even though it already runs eight tool selftests and this
  suite would fit that pattern exactly.

PROPOSED, STAGED IN THEIR OWN COMMIT SO IT CAN BE DROPPED WHOLE:
    .githooks/pre-commit                       runs the no-build set
    .github/workflows/port-defect-checks.yml   runs two of them on every PR
    port/tools/install_hooks.sh                opts a clone into the hook
  These are POLICY, not tooling. They change contributor workflow on a public
  repository, and the port has nothing in CI at all today, so adding the first
  thing is a standing-gap decision rather than a wiring detail.

  ONE OF THEM IS NOT AS INERT AS IT LOOKS, AND THIS IS THE PART TO READ. The
  usual claim for a tracked hook is that it does nothing until somebody runs
  install_hooks.sh. THAT IS FALSE HERE. The sm64ds-decomp clone at
  C:/Users/tango/Documents/sm64ds-decomp already has

      core.hooksPath = .githooks

  in its local config, shared by every worktree off it, and .githooks/ does
  not exist there yet -- which is the only reason nothing runs today. The
  moment that commit is checked out in that clone the hook is LIVE with no
  install step, on every commit touching port/, src/ or include/, at roughly
  a minute and a half a commit.

  It was live in this lane's worktree for exactly that reason, and it did
  work: the first commit on this branch ran the whole no-build set as a
  pre-commit and passed. That is a nice demonstration and it is still a
  workflow change nobody asked for. Turning it off afterwards is
  `git config --unset core.hooksPath`.

  The workflow file is genuinely inert until merged to a branch GitHub runs.
