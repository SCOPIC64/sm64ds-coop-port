THE PPU LAYER-BLENDING UNIT: ALPHA (BLDCNT mode 1) IN BOTH SOFTWARE RASTERISERS
Run link60 Stage 5, lane BLND1. Worktree C:/tmp/blnd1, branch s5-ppu-blend, off
cons 74f8a1aa5. Coordinator merges; this lane never merges or pushes.

WHAT WAS ADDED
--------------
The DS 2D colour-special-effects unit's ALPHA path (BLDCNT mode 1 + BLDALPHA),
including the always-on semi-transparent-OBJ alpha, in the port's two LIVE
software compositors:

  engine B (bottom screen)  port/ntr/ppu_sub.cpp
  engine A (top screen)     port/hal/message_compositor.cpp

Both already resolved pixels by priority; the change makes each resolve the TOP
pixel AND the one directly BELOW it, and when the top is a 1st target and the
below a 2nd target it outputs

  out = clamp31( top*eva/16 + below*evb/16 )     (BLDALPHA: eva bits0-4, evb bits8-12)

per channel, in 5-bit exactly as the hardware does. bgr555 expansion
(v<<3 | v>>2) is losslessly reversible by >>3, so the framebuffer's 8-bit
channels round-trip to the DS's 5-bit blend and back with no error.

An OBJ in mode 1 (semi-transparent) is ALWAYS a 1st target and ALWAYS
alpha-blends regardless of BLDCNT's first-target bits -- this is what makes
dScMgCurling_c's tint render, because its BLDCNT puts NO first-target BG bits up
(engine A 0x0d40, engine B 0x0440) and the effect fires only through the mode-1
shadow sprite. With no 2nd target beneath it a semi-transparent OBJ draws opaque,
as on hardware.

Window colour-effect gating: bit 5 of the window masks enables/disables the
effect per region; the blend is gated on (window_mask & 0x20) in both files.

BLDCNT layout (from the ROM's own G2x::SetBlendAlpha, src/_ZN3G2x13SetBlendAlpha
EPVttttt.cpp: *reg = ((a|0x40)|(b<<8)) | ((c|(d<<8))<<16), a=1st, b=2nd, c=eva,
d=evb, the 0x40 forcing mode bits 6-7 to 01):
  bits 0-5   1st-target select (BG0,BG1,BG2,BG3,OBJ,BD)
  bits 6-7   mode: 0 off, 1 alpha, 2 brightness-up, 3 brightness-down
  bits 8-13  2nd-target select

ESCAPE HATCH: SM64DS_BLEND_OFF=1 restores the old opaque path in both files
(read once via getenv, static-cached). Same binary, same .dsstate base, so a
before/after is the only comparison notes/port-selftest-bmp-gate.md permits, and
any regression bisects against the pre-blend image.

THE FADER DOUBLE-APPLY RULING (mission item 4)
----------------------------------------------
BRIGHTNESS (BLDCNT mode 2/3 + BLDY) is NOT applied by this unit. It is owned by
the existing fade path, and applying it here too would double every fade.

Derivation, from the code:
  * hal/fader_wipes.cpp HalFaderWipe::AdvanceFade writes BLDCNT mode 2 (white /
    brighten) or 3 (black / darken) + BLDY on BOTH engines via
    G2x::SetBlendBrightness at 0x40000{50,54} and 0x40010{50,54}, first-target
    0x3f. It NEVER writes BLDALPHA (0x52) and NEVER mode 1.
  * port_fader_blend_state() reads the RAW engine-A BLDCNT/BLDY (0x4000050/54)
    and returns evy+toWhite; walk_window's fade composite then dims the whole
    top framebuffer. So ANY engine-A mode-2/3 write is already applied globally.
  * The sub screen's fade is applied downstream too: ppu_compose_stacked's evy
    (engine A's) on the bottom half, and the corner panel inside walk_window's
    fade composite. ppu_scanout_sub separately applies MASTER_BRIGHT (0x6C), a
    different register the fader does not touch.
So the mode field partitions ownership cleanly: the game writes mode 1 for alpha
effects and mode 2/3 only for fades. blend_apply() returns the top pixel
unchanged for any mode != 1 (and for a semi-OBJ with no 2nd target), so a fade
frame is a provable no-op here.

PROOF (measured): scene 1 (SCENE_TITLE) runs an active BLDY brightness fade --
SM64DS_PPU_AUDIT over 60 frames read engine A BLDCNT 0x00bf (mode 2) / 0x00ff
(mode 3) with BLDY ramping 0x0f,0x0e,0x0d,0x0c,0x0b,0x0a and BLDALPHA 0x0000, on
both engines. Captured with SM64DS_SCENE_BMP at mid-fade frames 3, 5, 8 and 12,
blend ON vs SM64DS_BLEND_OFF=1:

  scene1 @frame 3    on-vs-off diff = 0 bytes
  scene1 @frame 5    on-vs-off diff = 0 bytes
  scene1 @frame 8    on-vs-off diff = 0 bytes
  scene1 @frame 12   on-vs-off diff = 0 bytes

Byte-identical while a fade is visibly progressing = the blend unit does not
touch the fade. (A second inertness check: level 1 boot frames 0..25, dumped
with SM64DS_DUMP_FROM/TO, vary hugely frame-to-frame as the 3D scene loads yet
are byte-identical ON vs OFF on all 26 frames.)

================================================================================
OBJ-VS-OBJ PRIORITY: THE TWO CURLING LAYERING BUGS (run link60, lane BLND2)
================================================================================

The owner playtested the shipped blend (0.2.8) in curling (scene 374,
dScMgCurling_c) and found two layering faults, both on the BOTTOM screen:
  1. the light-blue shadow tint drew OVER the bumper (the cursor/aim bar), which
     should render in front of the tint, untinted;
  2. the snow changed texture where it crossed a shell.

BOTH ARE ONE DEFECT, AND IT IS ON ENGINE B (ntr/ppu_sub.cpp). Measured on the
shot frame with SM64DS_PPU_AUDIT (scene 374, the shot driven by the in-exe
SM64DS_CLICK_TEST scripted stylus "256,724>256,584@100-119" in a focused
SM64DS_SCENE_WINDOW=1 run):

  engine A (top screen): mode-1 OBJ count 0 on all 160 samples. NOTHING blends
    on engine A in curling, so hal/message_compositor.cpp is not involved and
    was not touched.
  engine B (bottom screen): BLDCNT_B 0x0440 (mode 1 alpha, first-target NONE,
    2nd target BG2), BLDALPHA_B 0x1002 (eva 2/16, evb 16/16), and 5 mode-1
    semi-transparent sprites/frame. Only BG2 (priority 2) is enabled; every
    other playfield element is an OBJ. The blue tint is the semi shadow sprite
    alpha-blending over BG2.

  OAM (engine B, measured):
    shells   normal (mode 0) priority 1   OAM index 0,2,4,6,8
    shadows  SEMI   (mode 1) priority 2   OAM index 1,3,5,7,9   (the blue tint)
    cursor/  normal (mode 0) priority 0   OAM index 10,11        (the "bumper")
      bumper bar
    snow     normal (mode 0) priority 0   OAM index 13..60

THE RULE THE PORT HAD WRONG. raster_obj wrote g_obj[py][px] UNCONDITIONALLY as
it walked OAM 127->0, so the lowest OAM index always won -- pure index order,
"regardless of priority" as the old header note here even said. The DS does NOT
do that. OBJ-vs-OBJ is resolved by PRIORITY first, the lowest priority NUMBER
winning, and OAM index only breaks a tie. This is melonDS's DrawSpritePixel
verbatim (GPU2D_Soft.cpp): walking OAM 0->127 it overwrites iff the new pixel is
opaque AND (the slot is empty OR new prio < old prio). GBATEK's OBJ notes say the
same: a sprite's priority field orders it, index is the tiebreak.

  Bug 1: the shadow (prio 2, OAM 1) and the shell body (prio 1, OAM 0) both have
         a LOWER OAM index than the cursor bar (prio 0, OAM 10-11), so the old
         index-order write drew them over the bumper -- the semi shadow then
         alpha-blended over BG2 there, punching a blue notch through the bumper's
         gold outline. Priority order makes the prio-0 bumper win: it draws
         opaque, in front, and the tint only appears where the semi shadow is
         genuinely the top-relevant OBJ (which is what the DS does).
  Bug 2: the shell (prio 1, OAM 0) has a lower OAM index than the snow
         (prio 0, OAM 13+), so the old write drew the shell over the snow;
         the snow took the shell's texture wherever it crossed one. Priority
         order makes the prio-0 snow win -- it stays snow over a shell.

THE FIX (ntr/ppu_sub.cpp, raster_obj, ~6 lines). Before writing g_obj, skip if a
better-priority sprite already owns the pixel:

    if (g_obj[py][px].hit && prio > g_obj[py][px].prio) continue;

For the 127->0 walk this is exactly melonDS's "empty || new <= old": `<=` keeps
the lowest index on a tie (a lower-index sprite is processed later and overwrites
an equal-priority one), and a strictly-better priority wins whatever the index.
The resolver and blend_apply already read g_obj.prio/.semi, so the sprite that
wins by priority now drives the blend. NOT gated by SM64DS_BLEND_OFF: this is OBJ
resolution, not the alpha effect, so it applies to the OFF and ON paths alike and
the OFF-vs-on comparison stays contained to the curling blend region.
